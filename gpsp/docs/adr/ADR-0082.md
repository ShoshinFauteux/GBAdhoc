# ADR-0082: Present the ME-staged frame at the top of the loop; the ME reads the frame cached

- **Status:** current in code (part of the Stage-1 `me_video` path of [ADR-0080](ADR-0080.md)). The commit required hardware validation before it shipped to players; no record of that validation was found in the repo.
- **Date:** 2026-08-10 (commit `52446500`)
- **Source:** Reconstructed from the commit message of `52446500` and code comments in `psp/fe/merend.a.inc.c`, `psp/fe/loop.inc.c` and `psp/me/main.c`.

## Decision

Two coordinated changes:

1. In the ME module, `ME_CMD_COPY_PITCH` reads the source frame through the
   ME's data cache (invalidate the span, then read cached) instead of
   uncached. The destination stays uncached so the GPU sees it without an ME
   writeback. About 0.7 ms instead of 2.7 ms per frame.
2. Split the frame hand-off: `me_video_post()` at the end of the emulated
   frame gives the frame to the ME; `me_video_present()` at the top of the
   next loop iteration, before the core runs, retires the staged buffer and
   issues the GPU command list.

## Why

After the ADR-0080 offload, a GPU sync wait of about 1.3 ms reappeared on
heavy animation frames. The old main-CPU copy had been giving the GPU about
750 us of free overlap; without it the GPU only had the vblank slack to
draw in, which is zero when a frame runs over budget. Issuing the list at
the top lets the GPU draw during the whole ~12 ms core run. Latency stays at
one frame, because the faster cached copy finishes inside the vblank gap
between post and present. If the ME is not ready, the previous frame is
repeated and a miss is counted.

## Where in the code now

- `gpsp/psp/me/main.c` — the cached source read in `ME_CMD_COPY_PITCH`.
- `gpsp/psp/fe/merend.a.inc.c` — `me_video_post()`, `me_video_present()`.
- `gpsp/psp/fe/merend.d.inc.c`, `gpsp/psp/fe/loop.inc.c` — the post site and the loop-top present.
