# ADR-0060: The client's liveness ACK is unreliable and driven by silence

- **Status:** current
- **Date:** unknown; first committed 2026-08-09 in `276e4450`
- **Source:** Reconstructed from code comments in `rfu.c` and `libretro/libretro.c`, and the handover summary (HANDOVER.md §4.4 at `dba5e900`).

## Decision

1. Add `netpacket_send_unreliable()` and send the client's
   `NET_RFU_CLIENT_ACK` through it. Control messages (connect, disconnect,
   NACK) stay reliable.
2. Send that ACK only after one second of the client's own silence
   (`RFU_CLIENT_KEEPALIVE_US`), instead of once per host packet.

## Why

The client replied to every host packet with a CLIENT_ACK, sent reliably, so
it sent 1.92x the host's traffic (measured over 15 runs, per the code
comment), and each 16-byte liveness ACK occupied a queue slot and an
ARQ window slot (ARQ: the transport's acknowledge-and-retransmit layer) and
was itself retransmitted when late. The host uses the ACK for one thing:
resetting a client's time-to-live counter against a 240-frame (4 s)
disconnect threshold, and ordinary client data resets the same counter. A
lost one costs nothing.

It is rate-limited rather than deleted because a game whose client is
passive would otherwise drop off the host's roster after 4 s.

The handover summary records the result as traffic parity 1.92x to 0.96 and
retransmissions 1811 to 596.

## Where in the code now

- `gpsp/libretro/libretro.c` — `netpacket_send_unreliable()`.
- `gpsp/rfu.c` — `RFU_CLIENT_KEEPALIVE_US`, `rfu_cli_last_tx_us` and the send sites.
- `gpsp/sdl/main_sdl.c` — desktop decode.

## Notes

With scheduled adapter ticks (every frame sends a tick, which refreshes
`rfu_cli_last_tx_us`) the keepalive never fires. A quiet but connected
client was then dropped by the host; commit `8c1b1e00` fixed this by letting
any tick from a rostered client reset its counter. This ADR is unchanged by
that fix.
