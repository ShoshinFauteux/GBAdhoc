# ADR-0058: Instruments report every window, including zeros

- **Status:** current (applied as a general rule across the code)
- **Date:** unknown; first committed 2026-08-09 in `276e4450`
- **Source:** Reconstructed from code comments in `rfu.c`, `psp/fe/link.d.inc.c`, `psp/ff_psp.c` and `psp/me/me_mbox.h`. No ADR text was found.

## Decision

Add a periodic answer-latency census (`EVT rfu_answer_census n= max_us=`)
every 600 frames, emitted whether or not anything changed. More generally:
a probe whose silence could mean either "nothing happened" or "the probe is
dead" must emit a line every window, zeros included.

## Why

The [ADR-0055](ADR-0055.md) answer-latency event fires only on a new
maximum, so an all-zero session looked exactly like a probe that never ran;
the code comment says that is how several test runs read. With a census,
`n=0` means the probe is misplaced, and `n>0, max_us=0` means latency is
genuinely below one frame. 600 frames matches the existing profiler and
session-cost windows, so the lines sit next to the statistics they are read
against.

## Where in the code now

- `gpsp/rfu.c` — `RFU_TR_ANSSTAT`, `RFU_ANS_CENSUS_FRAMES` (600), and other censuses citing the rule.
- `gpsp/psp/fe/link.d.inc.c` — the `rfu_answer_census` event.
- `gpsp/psp/ff_psp.c` — pacing "hold" lines every ~10 s for the same reason ([ADR-0078](ADR-0078.md)).
- `gpsp/psp/me/me_mbox.h` — Media Engine mailbox states kept distinguishable by the same rule.
