# ADR-0059: Make the adapter's own deadlines observable, and allow them to be stretched

- **Status:** current (instruments always on in test builds; the stretch knobs are test-build keys, default 100 = stock)
- **Date:** unknown; first committed 2026-08-09 in `276e4450`
- **Source:** Reconstructed from code comments in `rfu.c`, `psp/fe/boot.inc.c`, `psp/fe/link.d.inc.c`, `netdrv/netdrv.h` and `frontend-common/netpacket_host.c`. No ADR text was found.

## Decision

1. **Instruments.** Trace the two timeouts the emulated wireless adapter
   enforces: the client's "your peer's data did not arrive in time"
   (`RFU_TR_TIMEO`), the host's synthetic "clients did not answer"
   (`RFU_TR_NORESP`), and the moment the game configures them
   (`RFU_TR_SYSCFG`). Each is reported at most once per emulated frame and
   only when it changed.
2. **Compensation knobs.** `rfu_timeout_scale` (client) and `rfu_rtx_scale`
   (host), in percent, 100 = stock, -1 = automatic (`session_fps / 29.97`).
3. **Transport counters.** Count standalone acknowledgement frames sent and
   received (`tx_ack`, `rx_ack`) in the netdrv transport.

## Why

The adapter's timeouts are counted in emulated CPU cycles, but the radio
underneath runs in wall-clock time, so the real budget shrinks as the session
frame rate rises. That was an inference in earlier findings, never a
measurement, because neither deadline had a trace hook and the game
overwrites the timeout without it being logged.

The knobs are explicitly not a fidelity fix. At 59.73 fps the emulator
already grants exactly what a real adapter would; at 29.97 it grants twice
that. What is unfaithful is the radio: PSP ad-hoc Wi-Fi takes around 55 ms one
way, against a few milliseconds for the real adapter.

For the transport: the client retransmitted about 31x more per payload than
the host and about 59 % of those arrived as duplicates, so the data got
through but the acknowledgement did not come back in time. The ACK counters
separate "ack sent late" from "ack lost on air".
