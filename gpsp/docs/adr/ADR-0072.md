# ADR-0072: Instruments for the client's lost input and the "return to lobby" error

- **Status:** current (with the "ADR-0072 fix" for the peak value)
- **Date:** unknown; first committed 2026-08-09 in `276e4450`
- **Source:** Reconstructed from code comments in `rfu.c`, `psp/fe/link.d.inc.c` and `sdl/main_sdl.c`, and the handover (HANDOVER.md §2, §4.3 at `dba5e900`).

## Decision

Add three wireless-adapter trace events, emitted per 600-frame window:

- `rfu_rxgate`: frames in which our model of the game's receive-queue depth
  exceeded 4, and the longest unbroken run of them. The model enqueues on
  each delivery and dequeues once per frame.
- `rfu_discans`: each time we told the game its peer disconnected
  (`RESP_DISC`), which produces the recoverable "press A to return to lobby"
  screen. Previously unobservable.
- `rfu_arrival`: host packets that arrived in the same emulated frame as the
  previous one ("clumping"), measured at the wire.

## Why

Emerald's `KeyInterCB_SelfIdle` (pokeemerald `src/overworld.c`) stops
reading the client's buttons while its link receive queue holds more than 4
entries. That queue drains once per frame and exists only on the client, so
the host cannot suffer this and the client can. The existing burst counter
was a high-water mark (it said a 9 happened, not how often) and was later
shown to count polls, not deliveries, so it could not answer the question.
The run length is what a person feels as "it ate my input".

## The "ADR-0072 fix"

The trace ring packs each argument into 12 bits, so the original `peak`
field (shifted left 16) always read 0. The peak now has its own event,
`RFU_TR_GQPEAK` (event 20).

## Where in the code now

- `gpsp/rfu.c` — `RFU_TR_RXGATE`, `RFU_TR_DISCANS`, `RFU_TR_ARRIVAL`, `RFU_TR_GQPEAK`, `rfu_gq_depth`.
- `gpsp/psp/fe/link.d.inc.c` — the event lines; `gpsp/sdl/main_sdl.c` — desktop decode.

## Notes

The handover (§4.3) warns that `rfu_rxgate n` over-reports sustained
saturation once the unbounded model passes 4; use it for onset, not level.
