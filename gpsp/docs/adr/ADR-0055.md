# ADR-0055: Measure the client's answer latency

- **Status:** current
- **Date:** unknown; first committed 2026-08-09 in `276e4450`
- **Source:** Reconstructed from code comments in `rfu.c`, `psp/fe/link.d.inc.c` and `sdl/main_sdl.c`. No ADR text was found.

## Decision

Stamp each host packet with the time it entered the client's receive queue,
and when the game consumes it, record how long it waited. Report a new
maximum together with the running mean (`EVT rfu_answer max_us mean_us`).

## Why

The `rfu_rx_cap` experiment (ADR-0042 in `../DECISIONS.md`) deliberately
delayed deliveries by a couple of frames, and the transport collapsed
(code comment: `txq_hi` 465, spill 81, the project's first `net_error`). The
wireless protocol punishes a late reply much harder than it punishes
volume, so the quantity worth measuring is how long the peer waited, not how
busy a frame was.

## Where in the code now

- `gpsp/rfu.c` — `RFU_TR_ANSWER`, the per-packet `t_us` stamp, `rfu_ans_*` counters.
- `gpsp/psp/fe/link.d.inc.c` — the `rfu_answer` event.
- `gpsp/sdl/main_sdl.c` — the desktop decode.

## Notes

A report that fires only on a new maximum cannot tell a quiet session from
a dead instrument; [ADR-0058](ADR-0058.md) adds a periodic census for that.
