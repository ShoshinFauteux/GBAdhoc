# ADR-0044: Stop dropping RFU payload on a burst; measure the queue depth

- **Status:** current (`RFU_PKT_QUEUE` is 64 at HEAD)
- **Date:** 2026-08-03
- **Source:** Reconstructed from the commit message of `2b40f0b7` and the comment above `RFU_PKT_QUEUE` in `rfu.c`.

## Decision

Raise the per-peer receive queue for wireless-adapter (RFU) packets from 16
to 64 slots, and add a trace event (`RFU_TR_QHI`) that reports the deepest
the queue has actually been.

## Why

The ADR-0043 flight recorder showed a client stalling for over a second
before a reset, and the host log showed about 55 `rfu_qdrop side=host_rx`
events where earlier sessions had 0 or 1. That was our own code throwing
away adapter payload, which the games cannot recover. A reliable transport
that has stalled delivers in a burst when it catches up, and 16 slots could
not hold one. The depth had been chosen by argument twice (4 to 16 in
ADR-0011, now 16 to 64) and overflowed in the field both times, so the depth
is now reported rather than guessed.

This overrides ADR-0041's advice not to raise the queue again. ADR-0042 had
tested that advice's theory on hardware and it failed. Queue depth does not
change how much the game is handed per frame; the game pulls one packet per
read at its own rate. Depth only decides how much can be held without loss.

The commit's gates: a desktop trade at 40 ms and 160 ms simulated radio
delay passed with no drops; the test rig peaked at depth 7 of 64.

## Where in the code now

- `gpsp/rfu.c` — `RFU_PKT_QUEUE` (64) with its history comment; `RFU_TR_QHI`.
- `gpsp/psp/fe/link.d.inc.c` — the `rfu_qhi` log line.

## Notes

The commit does not claim this was the root cause of the original
exit-Union-Room crash. The cost noted in the code is about 10 KB of BSS.
