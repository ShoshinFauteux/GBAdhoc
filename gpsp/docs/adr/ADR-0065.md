# ADR-0065: A protected priority window at the top of each frame (`emu_prio_boost_us`)

- **Status:** retired, falsified; shipped at 0 and removed from code in `4c0dcdcc` (2026-11-16)
- **Date:** unknown; first committed 2026-08-09 in `276e4450`
- **Source:** Reconstructed from the code comment in `psp/main_psp.c` at `276e4450`, the handover (HANDOVER.md §4.2 at `dba5e900`) and the removal commit `4c0dcdcc`.

## Decision (as proposed)

Keep the emulation thread below the Wi-Fi driver ([ADR-0062](ADR-0062.md)
b) as the default, but for the first `emu_prio_boost_us` microseconds of each
frame raise it above the driver (`emu_prio_boost`, default 0x29). A "warden"
thread lowered it again after the window, and the main loop also closed it
when the frame's work ended, so the window never reached into the vblank
wait. 0 = off, no thread created.

## Why (as proposed)

`emu_prio = 0x2B` is what let the link reach its target frame rate, but it was
believed to cost the join 3.5-4.0 ms of preemption per frame against a
16.74 ms budget. A mistuned window would degrade toward the working
behaviour, not the broken one.

## Why it was rejected

[ADR-0064](ADR-0064.md) counted 2.0 preemptions per frame, all by the
project's own transmit thread. The boost added one preemption (its own
warden) and removed none. The handover lists it under "Falsified, do not
re-propose".

## Where in the code now

Nothing. `PLAY_BOOST_US` and `psp/fe/boost.inc.c` were deleted in
`4c0dcdcc`; `gpsp/psp/fe/play_defaults.h` records that the fourth value of
the original ship stack left with its key. `gpsp/tools/refactor/fe_readme.py`
keeps a "gone" note.
