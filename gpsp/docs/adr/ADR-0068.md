# ADR-0068: The host also reads the network mid-frame

- **Status:** current (on in player builds: `PLAY_IDLE_POLL = 34952`)
- **Date:** unknown; first committed 2026-08-09 in `276e4450` (whose title names ADR-0068..0074)
- **Source:** Reconstructed from code comments in `rfu.c`, `psp/fe/boot.inc.c` and `psp/fe/play_defaults.h`, and the handover summary (HANDOVER.md §4.4 at `dba5e900`).

## Decision

Add `rfu_idle_poll_cycles`: while the emulated adapter is not waiting for an
event, poll the network every N emulated cycles (34952, about 1/8 frame). 0 =
never, the historical behaviour.

## Why

[ADR-0062](ADR-0062.md) d throttled a client that polled 587 times per frame.
The host had the opposite problem: it is waiting for an event only 0.6 % of
the time, so the only place it read the network was the single
once-per-frame transport pump. It sent replies immediately but did not look
for incoming commands until the frame boundary, which put up to a whole host
frame into the client's wait. This also re-read two earlier numbers: the
13-16 ms pump gap ([ADR-0061](ADR-0061.md)) is the host's receive
granularity, and a desktop round-trip of 16752 us (one frame) was an ACK
sitting unread.

## Measured (from the comment in `play_defaults.h`)

15 alternating runs at 59.73 fps, complete separation on both consoles
(p = 0.0002): host srtt 2.02 to 0.91 emulated frames, join 1.45 to 0.70. Not
free: host frames over budget rose about 6.5 points (median 9.49 to 16.03 %),
roughly 59.1 to 57.4 fps on the host only. Shipped on anyway because the
player build exists to complete trades.

## Where in the code now

- `gpsp/rfu.c` — `rfu_idle_poll_cycles` and the poll at the top of `rfu_update()`.
- `gpsp/psp/fe/boot.inc.c`, `gpsp/psp/fe/link.c.inc.c` — key and setter.
- `gpsp/psp/fe/play_defaults.h` — `PLAY_IDLE_POLL`; `harness-kit/HARNESS.md` documents the key.

## Notes

Both polls are now also gated by `rfu_sched_no_poll()` (scheduled adapter
ticks), which postdates this ADR.
