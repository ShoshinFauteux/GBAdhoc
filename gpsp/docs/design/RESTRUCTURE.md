# The main_psp.c restructure

This is a summary of the plan that split the PSP frontend `psp/main_psp.c` into modules and of the proof tools built for it. The original plan, its reviews and its run outputs are not kept in the repo. This page replaces them as the target of the citations in code comments. Section numbers follow the original plan, so a citation still lands on the right heading. Statements about what landed were checked against the tree. Measurements the plan quoted were taken at the time on the commits named. They are not re-measured here.

## Why split, and why fragments

A *translation unit* (TU) is one `.c` file plus everything it `#include`s: the unit the compiler sees at once. `main_psp.c` was one TU of about 18,300 lines (18,333 at 01067e74, about 18,650 at fbe9da63). It had about 480 globals in one namespace, a `main()` of about 4,500 lines with the per-frame loop inside it, and some 45 ways to end the process, about 20 of them pasted copies.

It could not simply be cut into separate `.c` files. GCC inlines many of its static functions into their callers and emits renamed clones that the hot-code order names. Moving code into another TU changes those decisions and the generated machine code. It also changes where code lands in memory, and the PSP's CPU instruction cache (*I-cache*: 16 KiB, 2-way, 64-byte lines) is sensitive to that. The plan cites a 160-byte move that measured about 3 % slower at the time. Most of the frontend also runs on a callback thread with a 4,000-byte stack (`cb_thread`, `fe/power.a.inc.c`), where extra call frames are a risk.

So the plan kept **one TU**. The file became a *shell* (`psp/main_psp.c`: includes, module info, `main()`) that `#include`s *fragments*, `psp/fe/<module>.inc.c` or, for a module cut into several pieces, `psp/fe/<module>.a.inc.c`, `.b.inc.c`, ... A fragment is a verbatim slice of the old file, included once, in the original order. The compiler sees the same token stream, so the release binary can be *byte-identical*: every loadable byte the same. A fragment may later be *promoted* to a real TU only under the rules of §1.1. That step is optional and has not happened.

## 0. Conventions, gates and corrections

### 0.1 Gates

A *gate* is a yes/no check that a commit must pass. A *flavour* is one of the three builds made from a tree: **release** (the player build, `GPSP_PLAYABLE`), **lab** (the test-lab build, with telemetry and rig hooks) and **harness** (rig build without the Lab hooks). `flavours.sh --against PARENT` builds all three, runs most gates and writes the gate line `gate.txt`. The line is generated by `flavours_gate.py` and never typed. Files are under `gpsp/tools/refactor/` unless a path says otherwise.

| Gate | Meaning | Implemented in |
|---|---|---|
| G0 | The preprocessed token stream (`psp-gcc -E -P`) of `main_psp.c` is identical, per flavour | `pp_diff.sh` + `pp_norm.py` (T3) |
| G0var | G0 on variant builds: every build switch alone and in pairs (`-E` only) | `pp_sweep.sh` / `pp_sweep.py` |
| G0R | A batch is a pure rename into module structs, or for release only a deletion of telemetry stores (added in the later code-health tier C) | `pp_diff.sh --rename-map` -> `g0r.py` |
| G1 | Every loadable (SHF_ALLOC) section matches by name, address, size and bytes ("G1-identical"); nothing loadable is masked | `sect_cmp.py` (T2), `det_check.py` |
| G2 | Per function: identical, identical apart from addresses, or changed; I-cache set of every hot-order function | `func_diff.py` (T1) |
| G2L | The frame loop compared by address, inlined helpers included (while it lived in `main`; now `frame_loop()`) | `loop_diff.py` (T1b) + `loop_anchor.py` |
| G3 | Layout report: key addresses mod 8 KiB, the loop's cache-set map, an audit that fails on unplanned `.text.unlikely*`/`.text.hot*`/`.text.startup*` sections | `layout_report.py` (T10) |
| HO | The hot order (`psp/layout/hot.ord`) still names real sections; its report equals the parent's | `hotord_check.py` (T5) |

| ST | Worst-case stack depth of `power_cb`/`exit_cb` against the 4,000 B `cb_thread` stack, library frames included | `stack_depth.py` (T12) |
| IC | Inline census: per function, emitted, cloned, or inlined into whom | `inline_census.py` (T13) |
| SS | Weak-override hooks and exported names are still strong and global | `strong_syms.py` (T6) |
| XS | Per exit site and flavour, the ordered teardown calls equal the golden matrix | `exit_matrix.py` (T8) + `tests/test_exit_model.c` |
| CI | Source rules: no raw `sceKernelExitGame(`/`handoff_run(` outside `fe_priv.h`, no `cold`/`noreturn` function without a section, no `pwr_hold` in hooks, no logic in `fe_evt()` arguments, ... | `ci_greps.sh` / `ci_greps.py` (T11) |
| ABI | Static asserts that the remaining hand copies of core declarations match the core headers; a per-flavour ratchet on their count | `abi_asserts.py` (T14), `flavours_gate.py ratchet` |

| CF | `tools/check_flags.py` exits 0 with the parent's output | `flavours.sh` |
| BF / DS | Build files are byte-identical / the diff stays inside `psp/main_psp.c` and `psp/fe/` | `step_scope.sh` |
| FP | Frame parity: the per-frame code of release and lab stays the same code at the same I-cache set, against a recorded baseline | [tools/layout/frame_parity.py](../../tools/layout/frame_parity.py) |

The plan also names gates that these tools do not run: **HT** (host tests, `tools/tests/`, `tools/run_ff_tests.py`), **G4** (the PPSSPP Lab correctness gate), **G5s/G5** (speed checks on hardware: a short sentinel set and the full bench suite) and **S / S-n** (the sleep/exit suite, §2.10). The gate line of a P step is `G0 G0var G1 G2 HO SS ST LL CF BF DS CI FP` (`REQUIRED` in `flavours_gate.py`). G2L, G3, LP, IC and XS are run beside it (`run_all.sh`, [tools README](../../tools/refactor/README.md)).

### 0.2 Corrections

While writing the plan, a re-read of the source overturned several assumptions that the earlier drafts shared. These are the ones code cites:
- **0.2-2.** The two `inproc_refusal()` calls in the teardown must stay separate. The second one can refuse *because* the first retain failed.
- **0.2-3.** A HOME press during the in-process return needs a sticky `g_exit_req` latch.
- **0.2-4.** Edits to teardown code move the loop too, because that code sat inside `main`'s address range.
- **0.2-5.** A `cold` or `noreturn` function without an explicit section can land in `.text.unlikely` ahead of `main` and move everything after it.
- **0.2-7.** The stall thread's exit was already routed through the exit-macro hijack.
- **0.2-9.** Before the loop left `main`, nothing held the loop in place: any size change before `main` moved its cache sets.

## 1. Target architecture

### 1.1 Physical shape and the promotion rule
`main_psp.c` stays the one TU for everything hot, inlined, or reachable from `cb_thread`. A fragment may become a real TU only if all of these hold: (a) none of its functions is inlined into another module (IC); (b) none is in the hot order; (c) G2 shows only address changes; (d) ST holds if it is reachable from the callbacks; (e) SS is green. Power, audio, pacing, the ME presenter (the renderer on the PSP's second CPU, the Media Engine), the frame loop and the io thread are never TUs, by rule.

### 1.2 Module list
About 20 modules: paths, audio, iothread, input, power, display, merend, pacing, rewind, link, mgift, misc, inproc, teardown, boot, session, loop, harness, plus the shell and two headers. The cut itself is `tools/refactor/cutlist.txt`: one row per function and per global, generated by `split.py gen` and reviewed once, so no item is unassigned or listed twice. The generated module table, with owners, fragments and `#if` context, is [psp/fe/README.md](../../psp/fe/README.md). The plan's `boost` module has no fragment at HEAD.

### 1.3 Ownership and globals
A global is defined in its owner module's fragment; `globals.py` (T9) takes owners from the cutlist and reports writes from other modules. Writes from another module go through a function, except on the hot path (pacing, merend, loop), where accessors are forbidden. State the callbacks touch keeps its declarations and is never folded into a struct, and LTO is not used. Exported names (`g_dir_base`, `g_running`, `g_ff_uncapped`, `g_ff_mult`, `in_rate`, `g_audio_step`, `g_net_up`, `g_net_is_host`, the weak-override hooks, and `gpsp_net_wait_beat` in rig builds) keep their names and linkage; SS checks them.

### 1.4 Headers
`psp/fe/fe_priv.h` holds the TU-private macros (private to `main_psp.o`), and `psp/fe/play_defaults.h` holds the ship constants. The plan named a `psp/main_psp.h` for the exported names. There is none at HEAD: the users declare them (for example `psp/ff_psp.h`). `fe_abi_asserts.h` cannot be included from `fe_priv.h` because it needs core headers. It is generated per flavour into `tools/refactor/generated/<flavour>/` and compiled in a separate check TU. Since tier C the TU includes `gpsp/core_fe.h` instead of copying core declarations.

## 2. Staged milestones

Every step builds all three flavours. Release is compared with release, and lab with lab.

- **Phase T (tools).** The tools of §5 were built first, with no frontend edit, and proven on two clean builds of 01067e74 ([baseline.md](../../tools/refactor/docs/baseline.md)). Landed.
- **Phase P (pure, byte-identical, no hardware).** This was redone on the beta.5 base; see the Phase P section below. P1-P6 have commits, and the split (P4) landed: `psp/fe/*.inc.c` exist.
- **HW-1 (sleep-path fixes).** Verified at HEAD: F2 (`pwr_hold("teardown")` before `play_lock_drop` in `session_end`), r7-L5 (the boot hold is taken when the browser returns, `fe/session.inc.c`) and r2-B-5 (`y <= g_wake_h` in `fe/display.c.inc.c`).
- **HW-2 (exit, UI, config, net fixes).** Verified at HEAD: F1 (`g_exit_req` in `exit_cb`, `g_running = !g_exit_req`), F3 (`ui_settings_flush()` in `session_end`), and the stall thread's exit through `FE_EXIT_GAME_STALL` / `pwr_release_kernel`. The status of the other items is not recorded here.
- **HW-3 (epoch C, the cold restructure).** One teardown sequence, `boot_run`, session phases and a `for (;;)` in place of the `goto`. Landed: see §3, §4 and [EPOCH-C.md](EPOCH-C.md). C4 (regrouping fragments by module) did not happen: the fragments are still in source order.
- **HW-4 (D1: the loop leaves `main`).** Landed in a different shape: `frame_loop()` in `fe/loop.inc.c`, noinline, in `.text.startup.fe_frame_loop`, placed by `pin frame_loop` in `tools/layout/layout.lock`. The planned `frame_iter`/`frame_iter_rare` split was not made. Separately, the hand-tuned layout pads were replaced by `pin` rows in `layout.lock` (see [LAYOUT-PINNING.md](../LAYOUT-PINNING.md)).
- **HW-5 (D2: optional per-frame trims).** Status not recorded here.
- **HW-6 (PSP-1000 heap).** The wake frame is 161 rows (`WAKE_ROWS`). The audio ring is still 16384 frames, and the main stack is still 256 KiB. Other items: status not recorded here.
- **M-late (real-TU promotions).** Not done: every fragment is still included by the shell.

### 2.10 The S suite (sleep/exit), through the real menus
Run on the hardware rig, never as a speed test. S-1 is sleep and wake in play, in the menu and on the wake overlay. S-2 is repeated quit-to-game-list with the heap census. S-3 is quit after a standby, which must relaunch. S-4 is HOME to the XMB in four arms, two of them during the return to the game list. S-5 is a power slide just after a quit (three arms). S-6 is sleep during boot and in the browser. S-7 is a link-session quit on two consoles. S-8 is Mystery Gift start and stop. S-9 is a slow or watchdog ME teardown, then sleep, plus the sleep-simulator mutant that fails the ME sync.

## 3. Exit-path unification

- **3.1** lists the endings: families A (harness boot probes), B (game-list exits), C (load and net failures), D (the shared loop teardown) and E (out-of-band exits, which stay out).
- **3.2** gives the canonical teardown, steps D0-D20, in the order the source ran them, and the in-process return. That return has an atomic unload unit (`inproc_unload`) and a heap-census contract.
- **3.3** covers the flags and the per-site ORDER selector, which reproduces each site's historic order.
- **3.4** keeps `stall_exit` and `exit_cb` out of the shared sequence.
- **3.5** lists the deliberate differences that were kept.
- **3.6** defines the XS proof.

Epoch C carried this out: `exit_early_begin`/`exit_early_end`, `session_end`, `inproc_unload`, `inproc_try_return` and `process_end` in `fe/teardown.inc.c`. See [EPOCH-C.md](EPOCH-C.md) and [INPROC-RETURN.md](../INPROC-RETURN.md).

## 4. main() state machine

- **4.1** gives the states: BOOT, SELECT, CONFIGURE, LOAD, NET_UP, PRE_LOOP, RUN, TEARDOWN, INPROC_DECIDE, then SELECT again or EXIT.
- **4.2** makes `main()` a plain sequence of phase calls, with no dispatch table or `switch` loop.
- **4.3** sets the rules. The path buffers and process-lifetime counters stay in `main`'s frame and are never zeroed per game. Phases are `noinline` with explicit sections. Per-game state is reset in one place. `g_running` stays volatile.
- **4.4** keeps the boot order unchanged.

This landed in Epoch C (see [EPOCH-C.md](EPOCH-C.md)). `main()` in the shell is now `boot_run`, then a `for (;;)` over `session_select`, `session_configure`, `session_load`, `session_net_up`, `session_pre_loop`, `frame_loop`, `session_end` and `inproc_try_return`, then `process_end`.

## 6. Latent bugs

The maps of the old file found real bugs. Examples: a HOME press during "Returning to game list" was lost, there was a power-lock gap at quit, and some network failures were reported as "WLAN switch is OFF". The rules: a fix is never part of a move commit, each fix is its own commit with its own test, and fixes reach hardware only in the HW-1 or HW-2 candidates. Items that would change behaviour on purpose were left to project decisions rather than fixed as bugs.

## 7. Speed and heap

These were estimates at the time and are not claims. The loop placement was the only item expected to show above measurement noise, in either direction. The other per-frame trims were expected to be below noise. They were to be accepted only as "no regression". Heap items on the PSP-1000 count byte for byte when they are allocations, and in 8 KiB steps when they are image sections.

## 8. Sequencing

Nothing in this plan touched `main_psp.c` while the optimisation loop was editing it. Each step had at most one layout event, and only one build waited for hardware at a time. Branches that edited `main_psp.c` either landed before the split or went in through `split.py replay`, never by a hand merge onto fragments.

## 9. What not to do

The rules are fully listed in the original plan; these are the main ones:
- Don't promote power, audio, pacing, the ME presenter, the loop or the io thread to TUs.
- Don't hand-merge or hand-edit fragments.
- Don't put a fix or a rename into a move commit.
- Don't count a step as pure from its C diff: only G0/G1, or G2 plus G2L, say so.
- Don't merge the two `inproc_refusal()` calls.
- Don't add a `cold` or `noreturn` function without a section attribute.
- Don't trust stale numbers.
