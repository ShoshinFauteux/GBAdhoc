# Unbound and Heart & Soul M4A mixer optimization review

**Status: provisional safety review; PSP Go freeze remains unresolved.** This review traces the current source and the recorded hardware results. It does not certify the current configuration as safe for long play. The matched full/control diagnostic pair has not been run on a PSP Go.

## 1. What is being optimized

Unbound and Heart & Soul use a GBA M4A-family sound engine that copies or rewrites small ARM instruction sequences in GBA IWRAM while the game is running. gpSP's dynarec translates GBA code into native PSP code. When a guest write overlaps translated code, the conservative response is to flush the RAM translation cache and translate code again. The mixer does this often enough to become a major cost, especially with the heavy soundtrack.

The current fast path recognizes a *shape of store*, calculates the write interval, and retires only overlapping translations. It is not selected by game title or ROM header. The Media Engine renderer is a separate subsystem; its frame composition does not execute the guest CPU or its M4A mixer.

## 2. Active levers and their risks

The release profile in `tools/build.sh` enables `SMC_GATES`, `SMC_GATES_SIMPLE`, `SMC_GATES_RANKED`, `SMC_GATE_BITMAP`, `SMC_PARTIAL_SAFE`, `SMC_PARTIAL_STABLE_THUNK`, `SMC_PARTIAL_DIRECT_LINKS`, `GBA_PC_MASK`, and `BADJUMP_SAFE`.

| Lever | What it changes | Evidence and risk |
| --- | --- | --- |
| **Ranked SMC gates** (`SMC_GATES_RANKED`) | Learns frequently modified guest addresses; a normal candidate needs 64 observations and at least half must change the stored word. | Helps split hot code so invalidation and retranslation affect smaller blocks. Evidence: the hot H&S mixer location had 62,953 changed writes versus 120 same writes; a nearby data word had 1 changed write versus 66 same writes. The active profile does not enable `SMC_GATES_SNAP`, `SMC_GATES_SNAPF`, or `SMC_GATES_CODED`: `SMC_GATE_PICK` rounds the write address down, and promotion does not prove it is a real instruction boundary. A mutable data word could therefore still earn a gate if it meets the frequency/change threshold. Counters persist for the whole ROM session; soundtrack/code-role changes do not restart evidence, so a candidate can inherit history from an earlier role. |
| **Add-only gate placement** (`SMC_GATES_SIMPLE`) | Adds a learned gate in a free slot and never relocates an existing one. | Avoids the historically crashing eviction behavior, where live translations and a moved gate table disagreed. It is safer than relocation, but gates still affect where future translation starts. The table is finite (8 slots by default); when full, new ordinary gates are ignored. |
| **Gate bitmap** (`SMC_GATE_BITMAP`) | Makes gate membership checks use a bitmap rather than searching the live list. | Intended as a lookup-cost optimization with the same boundaries. No isolated hardware speed or crash result was found for the bitmap by itself. |
| **M4A-shaped writer classifier** (`smc_writer_safe_range`) | Accepts a non-writeback ARM `STMIA` through `LR`, with a non-empty register list and a final checked address within `0x200` bytes of the writer; derives the interval from the list length. | The shape was observed on hardware: Unbound's measured offset was `0x3c`; H&S heavy-track writers covered `0x48` through `0x148`, with four writer sites and 16 deltas. The predicate has no ROM identity, fixed writer PC, or target-region check. Another routine with the same shape can be accepted. The `safe` in the helper name is a design label, not proof that all matches are safe. |
| **Direct range-endpoint gates** (`smc_partial_install_range_gate`) | Adds the computed first and final written words as gate addresses. | This bypasses ordinary ranked evidence and code-boundary filtering. The endpoints persist across soundtrack changes until ROM load. A non-code endpoint can make the scanner translate data as instructions; historical bad gates produced invalid guest branches and a crash. No trace proves the present M4A rule installed a bad endpoint. A source audit found a capacity edge in the old readiness check: if low was already gated but high could not be added to the full table, selective retirement could proceed after checking only low. The guard candidate now requires both normalized endpoints; absent either, it takes the existing full-flush path. |
| **Selective range retirement and SMC store coverage** (`flush_translation_cache_ram_range`, `SMC_SP_CHECKED`) | Retires translations intersecting an accepted store interval; the optional switch routes SP-based block stores out of their unchecked fast path. | This is the highest-risk area. Most generic ARM/Thumb block stores check only the final word; intermediate words use unchecked aligned stores. The default Thumb `PUSH {..., LR}` form is an exception: both its register-list stores and extra LR store are unchecked. In the default profile, ARM stores through SP and Thumb's SP-based `PUSH` fast path can also bypass SMC checks on every word. `SMC_SP_CHECKED` disables that SP fast path and makes the final word checked; it also changes Thumb `PUSH {..., LR}`'s LR store from unchecked to checked. It still does not check every word, so a block whose earlier word overwrites translated code while its final word does not can remain undetected. When a checked store raises the SMC handler, the measured M4A classifier uses LR as its base; for its accepted path it reconstructs the full non-writeback STM interval, and unsupported forms take the full flush. An unchecked interior write can bypass the handler entirely if the final checked word misses translated code. The observed writeback stack-copy shape is rejected, but the predicate does not semantically classify every kind of copy. |
| **Stable entry thunks** (`SMC_PARTIAL_STABLE_THUNK`) | After `smc_partial_active` is set, keeps a stable entry for translated RAM blocks so a retired block can redirect to the dispatcher rather than leave stale inbound branches targeting abandoned code. | Addresses the real stale-link hazard created by partial retirement. It changes generated code and layout. It was not independently benchmarked; the recorded performance increment combines it with direct RAM links. |
| **Direct RAM links** (`SMC_PARTIAL_DIRECT_LINKS`) | While `smc_partial_active` is set, leaves ordinary RAM-to-RAM branches direct while routing persistent ROM-to-RAM links through an island. | Reduces dispatcher overhead, but a missed or incorrectly retired inbound link could keep stale translated code reachable. The stable-thunk mechanism is a required safety partner. Hardware evidence isolates the pair, not each lever. |
| **GBA PC masking** (`GBA_PC_MASK`) | Applies the GBA's 28-bit guest address behavior before region lookup. | Correct guest address semantics. It is not a safety boundary by itself: masked garbage can still land in a region the translator handles. |
| **Bad-jump containment** (`BADJUMP_SAFE`) | Resets the emulated GBA when the runtime dispatcher receives an unmappable guest PC, rather than jumping the PSP CPU to it. | Prevents a class of native jumps from the dispatcher, but recovery resets the game. It cannot catch a direct MIPS jump emitted earlier by a translator path that bypasses the dispatcher. The older `0x0FFFFFFC` sentinel-jump bug was fixed; it has not been shown to be the Go freeze. |

**Not active in the current release profile:** 128-byte gate clustering (`SMC_GATES_CLUSTER`). The profile enables `SMC_GATES_SIMPLE`; clustering is a separate compile-time branch. Do not attribute current performance to that clustering rule.

The source-level stale-link defense is coherent: after partial-safe activation, RAM translations expose stable entry thunks; RAM-to-RAM links can point directly at those entries, and retirement rewrites a retired thunk to redispatch the guest PC. ROM-to-RAM exits get dispatcher islands because ROM translations survive a RAM-cache flush. Range retirement checks its bounds and each candidate block's recorded extent before patching any thunk; invalid bounds or missing metadata take the full-flush path. If preserving cleared guest tag words overflows the retired-tag table, it also falls back to a full RAM flush. This removes an obvious stale-pointer path by construction, but it does not prove the Allegrex instruction-cache synchronization and live hardware behavior are correct; the Go A/B remains necessary.

There is a separate hole in SMC coverage that the matched `full`/`control` comparison cannot test: both arms leave the unchecked SP-based block-store fast paths enabled. The ARM SP store and Thumb `PUSH` emit inline stores that do not notify the invalidator for each word. `SMC_SP_CHECKED` routes those paths through a checked final-word store, but still does not check every word in the block; it is a probe, not a complete coverage guarantee. The available `spchecked` build changes this behavior, but has no matched PSP Go soak result. Thus a clean `full`/`control` result would not rule out a write through either SP fast path as a stale-code source.

### Adjacent sound-path hazards (not established as the freeze cause)

- **Zero direct-sound timer step:** the prior 8.24 conversion could truncate a valid very fast timer to zero; `sound_timer()` then had a progress loop that could not advance. Current `direct_sound_timer_step()` uses 64-bit division and saturates high steps, and `sound_timer()` immediately returns on zero, so that specific infinite loop is guarded. The focused `test_sound_timer_step.c` checks the arithmetic helper, not the consumer's full loop or PSP timer behavior. This is a fixed historical hazard, not evidence for the present Go freeze.
- **PSP audio-thread output and teardown:** a negative `sceAudioOutputBlocking()` result now stops the worker and reports the error, avoiding an immediate-return retry loop. `audio_stop()` still waits synchronously for the worker to end; if the PSP audio call itself never returns, teardown can wait indefinitely. That is a conditional API-hang risk, not a demonstrated cause of a freeze while the game is running.
- **Resampler signed overflow:** the PSP output interpolation multiplies two signed `int` values, `(l1 - l0) * f`, where opposite full-scale samples can make the product exceed `INT32_MAX`. In C that is undefined behavior. It could affect output samples or compiler-generated behavior; no evidence ties it to a full-console freeze, and the current PPSSPP audio-hash comparison does not exercise Allegrex code generation.
- **Malformed savestate fields:** `sound_check_savestate()` bounds the direct-sound FIFO/ring indices and several PSG fields, but does not validate every PSG state field before `sound_read_savestate()` installs them. The unchecked fields can affect array indexing or arithmetic in PSG rendering. This is a corrupted/malformed-state risk; it does not explain a normal-play freeze unless a state-load path or damaged state is involved.

These items broaden the audio audit beyond the M4A self-modifying guest code, but none currently proves the freeze cause. The endpoint-gate readiness gap is a separate, concrete correctness-contract issue and has a focused diagnostic build described below; it is a candidate fix, not yet a confirmed explanation for the PSP Go shutdown.

## 3. What the benchmarks establish

The strongest recorded M4A-specific result is commit `e501964`: Heart & Soul heavy-track work fell from 15.317 to 9.567 ms/frame on one PSP and from 15.468 to 9.651 ms/frame on a second; reported rate moved from about 57 to 59.8 FPS, while translations per measurement window fell from 107,416 to 10,778. The same record reports a 4.8% gain on the light track. Unbound's SMC translation count was unchanged by that M4A-family expansion, and its rate remained at 59.96 FPS, while measured work/frame rose 1.28% and 1.45% on the two consoles. This supports the claim that the generalized matcher recovered H&S mixer work without an observed Unbound frame-rate loss in those fixtures, but not without any CPU-work cost; it is not proof for all titles, tracks, or long sessions. The numeric H&S probe/performance summaries are recorded in the commit message and source comments; their raw probe and run logs are not preserved in this checkout, so those exact measurements cannot be independently recomputed here.

The later `sprt17b` fixture was measured on a PSP-1000 over the same 3,600-frame scripted battle: it averaged 59.366 FPS for Unbound and 59.810 for H&S, including the costly battle transition; Unbound's steady combat windows were near the GBA's full rate. That build also included stable-thunk/direct-link and renderer work. It cannot assign the full gain to the mixer path. Likewise, the `sprt09` to `sprt12` comparison combines stable thunks with direct links; the pair rose from 50.853 to 53.504 FPS on the Unbound fixture, but does not isolate either lever. The later `full`/`control` freeze A/B has no hardware performance result, so it cannot tell us what speed a conservative full-flush fallback retains. The host test `tools/test_smc_safety.c` separately mirrors the writer predicate and explicitly accepts an unrelated EWRAM STMIA/LR writer with the same shape. That demonstrates the classifier is not title-specific. Because the test reimplements the logic instead of calling the production helper, it cannot catch drift between the model and `cpu_threaded.c`. It also does not execute production ARM/Thumb store emitters, walk real translation tags, validate emitted thunk/link patches, or exercise PSP cache maintenance. The existing `spchecked` arm is the only retained comparison that changes the SP fast path, and it has only short PPSSPP output checks, not hardware freeze evidence.

These are fixture results, not a maximum safe FPS. H&S reached 59.810 FPS on the measured PSP-1000 fixture; Unbound averaged 59.366 over the full fixture and approached the GBA rate during steady combat. There is no performance score for the current full-flush control and no universal safe ceiling or validated full-speed configuration while the Go freeze is unexplained.

## 4. Abandoned approaches and documented traps

- Retiring one block at a time was fast but left stale M4A translations; the audio hash changed despite identical video. Do not treat that 59.9 FPS result as a valid optimization.
- A flat 4 KiB invalidation window was slower than the prior build (26.9 versus 29.4 FPS in its recorded fixture).
- Treating every single SMC store as safe for partial retirement caused Heart & Soul's copy loop to leave stale code and white-screen. The observed writeback stack-copy shape is rejected by the current M4A predicate; that writeback-bit check is not a general detector for copy semantics.
- Evicting or moving gates while translations remained live crashed Heart & Soul. Current simple gates are add-only.
- The idempotent-store filter (`SMC_SKIP_SAME`) is documented in the source and build notes as a prior single-variable PPSSPP failure: Heart & Soul white-screened at boot and emulated CPU progress stopped. The original run log is not preserved in this worktree, so treat this as documented historical evidence rather than independently reproducible evidence. The switch is opt-in in the Makefile and absent from the matched PSP full/control build flags, so it does not explain those builds unless another binary enabled it. Keep it classified as a rejected experiment, not an active optimization.
- Tightening the writer fingerprint with unverified IWRAM/PC/repetition requirements degraded hardware performance because false rejection returns every mixer write to a full flush. The added requirements were withdrawn.
- Candidate staleness windows and clearing learned gate state on same-ROM reset/savestate/cache flush were withdrawn after performance regressions. Current source clears ranked evidence on ROM load only. A narrower state-load correction now rebases each candidate's remembered guest word after a successful restore while preserving its accumulated hit/change counts. This prevents a single pre-load-to-post-load value difference from counting as fresh self-modification, without paying the thousands-of-frames relearning cost. The fix is in the current investigation worktree and remains untested on hardware; it addresses a demonstrated accounting flaw, not a proven cause of the Go freeze.
- The old eager translator could encode its unmappable sentinel as a direct MIPS jump to `0x0FFFFFFC`, outside PSP RAM. That defect had a concrete mechanism and was corrected by routing unresolved exits to a shared known-good entry without emitting code. Earlier per-exit dispatch islands added translation-cache pressure; their measured performance regression was later removed. Neither history proves the current Go freeze's cause.

## 5. Freeze evidence and unresolved questions

The PSP-3000 H&S evidence from 2026-09-21 comes from a different, incompletely versioned EBOOT. `badjump.txt` contains three identical unmappable guest targets (`0x04e3a020`), each followed by a recovered GBA reset. Its snapshot lists gates `0300168c`, `03001688`, `03007cd4`, and `03007c7c`; the first two match the current classifier's computed high/low endpoints, while the old binary's missing source manifest prevents attributing the other two to a specific rule. This is a concrete bad-control-flow event, but it was contained as a guest reset and did not itself prove a whole-PSP freeze. Separately, the preserved frontend log ends at frame 55,319 of an 82,500-frame job. It has no run IDs to associate that cutoff with any bad-jump record; the stop could be a freeze, manual stop, or interruption. The `prev lookup pc` is the last successful lookup, not the bad branch instruction. The nearby ROM callback path is a lead, not a demonstrated cause. No record ties those resets or the log ending to the PSP Go power-off.

The reviewed PSP Go freeze remains unexplained. Plausible software paths include an SMC/gate or stale-translation fault outside the contained runtime-dispatch path. The ME renderer is a weaker explanation for a CPU hard freeze, but only hardware can test it; PPSSPP does not run the PSP Media Engine. Heat or power behavior also has not been excluded by controlled evidence.

Fast-forward is a workload amplifier in this build, not a mode that skips the guest sound code. In the user 3× multiplier mode, `g_ff_mult` makes `psp/main_psp.c` call `fe_host_run_frame()` three times per outer loop, and each call invokes `retro_run()` for another complete GBA frame. Uncapped mode instead runs one guest frame per loop and removes the normal vblank pacing, so the loop keeps running as quickly as the PSP permits. In both modes, `retro_run()` executes the GBA CPU and then runs audio generation; `plat_audio_frames()` may mute/drop samples only after they have been produced, but that does not skip the game's M4A code or its SMC writes. The captured harness specifically starts with `ff=0` and its script issues `ff on`, which selects uncapped harness mode; it is not a measurement of the user 3× loop. Its final telemetry window reports 73.48/72.20 emulated FPS on the PSP-1000/3000, about 1.23×/1.21× the GBA's 59.73 FPS rate. This makes the user's “FF makes it fail sooner” observation consistent with more guest frames and SMC events per wall-clock second, as well as greater sustained CPU/thermal load. It does not prove which factor causes a PSP Go shutdown; there is no temperature, voltage, or Go trace to separate them.

A documentation discrepancy remains important when reading history: the early narrative in `STABILITY-FIX-2026-09-17.md` says ranked candidate state was cleared at emulator reset/cache flush. The current source and `CURRENT-STATE.md` say ROM-load only; the later correction in that narrative withdraws the broader reset rule.

That switch routes SP-based block stores through the checked final-word path; intermediate words remain unchecked. The recognized M4A store specifically requires LR as its base, so `SMC_SP_CHECKED` does not change whether that store matches the M4A classifier; it probes the separate SP-store fast path and its generated-code/layout effects. A difference from `full` would implicate that switch or its layout effect, not prove a particular stale store caused the freeze.

Run both on the same PSP Go with the same Unbound and H&S save states, soundtrack settings, and repeated fast-forward toggles, changing ROMs without exiting GBAdhoc when that reproduces the reported sequence. Current code clears learned candidate state on ROM load, so same-process switching tests lifecycle/order but not cross-ROM candidate carry-over. Verify the installed EBOOT hash, cold-start between arms, repeat/interleave runs, and record termination, SMC/range gates, flushes, frame count, and any recovered bad jumps. A freeze only in repeated `full` runs implicates the broader partial-safe runtime activation group, but not a single mechanism within it. If both arms freeze, that shows the group is not necessary under those tested conditions; interactions with it are still possible. A second one-lever pair would be needed to separate endpoint gates, selective retirement, and the thunk/link-policy changes.

The same two EBOOTs also support a config-only three-state ME factor: renderer plus PRX, PRX loaded with renderer off, and ME fully off. `me_mode=0` alone only disables the renderer; `me_boot=0` in `CONFIG.INI` is required to stop loading the module. Crossing those ME states with `full` and `control` will distinguish a renderer-dependent freeze from one associated with module startup, and show whether either interacts with the selective-SMC group. ME-off also changes scheduling, memory use, and heat, so even a clear difference establishes dependence rather than a specific memory-corruption mechanism. Exact overrides and expected startup logs are in `builds/hns-freeze-matched-2026-09-24/TESTING.md`.

### Endpoint-guard candidate (source fix, hardware result pending)

The endpoint invariant is now enforced at the decision point: selective retirement requires both the low address and the last-written word (`partial_high - 4`) to exist in the gate table. This matches the installer, which normalizes and attempts to install the same two endpoints. If an endpoint is absent, the caller uses the established full RAM-cache flush. The added gate lookup has a small cost on each eligible event; the larger performance cost occurs when a missing endpoint forces a full flush, which is most likely when the gate table is saturated. This preserves correctness by refusing to rely on a partially established block layout. The former state was a real contract gap, but the retirement routine also validates the endpoint tag and falls back if it is invalid, so static analysis does not prove it caused a crash.

I built a diagnostic `endpoint-guard` arm from the frozen 2026-09-24 matched-build source plus only this readiness condition. EBOOT SHA-256 is `cce5759a70986bed6f5b93c07ed2aa07ab5d0a40a34187cfc11eb7298de0acec`; its ME PRX SHA-256 matches the existing arms at `7612a2e1425150ad32006025a43c4252dff6eb1355164de18a9abb19243ef098`. The PSPDEV image and shared instrumentation/profile match the earlier soak build. The patch compiles for PSP. No Go or other-console runtime test has been performed on this new EBOOT, and it has not been installed. Exact artifacts and run instructions are under `builds/hns-freeze-endpoint-guard-2026-09-24/`.

At present, no combination can honestly be called both full-speed and safe on the Go. Disabling the partial-safe runtime group returns SMC events to full RAM-cache flushes and avoids this selective-retirement risk, but ordinary ranked/add-only gates and the rest of the dynarec remain active. Its title-specific FPS has not been measured as a long-session Go baseline. The current maximum observed fixture rate is approximately 59.8–60 FPS; the maximum safe rate remains unknown until the Go A/B and long-session validation complete.

Existing PPSSPP comparisons give limited but real guest-output evidence. In the short H&S-heavy test, `full` and `spchecked` have the same 501 input events and state-load result, then identical 1,001-frame video-hash sequences (frames 1–1,001), identical audio hash `0b86fceb` over 548,916 samples, and both exit normally. This is one deterministic sequence, not a long-session stability test. Separate longer runs have identical recorded video-hash sequences over 4,012 Unbound frames (300–11,524) and 3,799 H&S heavy-track frames (300–7,152), but report zero audio samples. Together these show no observed guest audio/video output difference from `SMC_SP_CHECKED` in the sampled PPSSPP runs. They cannot establish PSP Go stability, physical Allegrex cache behavior, or Media Engine behavior.

## Investigation update — savestate candidate values (2026-09-24)

The ranked gate learner stores a last-observed word alongside each candidate's hit/change counters. A savestate restores guest RAM and the frame counter, and flushes translated code, but the learner's counters and remembered words persist. At most one observation per candidate can be stale: if that value differs from the restored word, the next store can be counted as a change even if it simply rewrites the restored value. The stale observation cannot bypass the 64-hit minimum. It can only promote a row already at the edge (for example, 63 hits/31 changes becoming 64/32), which could place a false ordinary gate if a slot remains. This is a proven accounting flaw, not a proven PSP freeze cause.

A fresh call-site audit confirms the refresh is narrowly scoped: `smc_gates_refresh_values()` is called once, at the end of `gba_load_state()` after component-state reads and memory restore succeed (`savestate.c:278`); the call is inside `HAVE_DYNAREC` but outside the `dynarec_enable` condition. `smc_cand_forget()` is only reached through `smc_gates_reset()`, whose only external call is the ROM-load path in `gba_memory.c:3326`. Thus successful savestate loads rebase values, while same-ROM reset, soundtrack/code-role changes, and other cache flushes preserve candidate hit/change history. Those role-change cases remain untested on the PSP Go and are more directly aligned with the reported soundtrack correlation than the repaired savestate-only stale comparison; that is a prioritization of the next experiment, not evidence of causation.

A narrow correction refreshes only remembered words after every successful state restore (and after cache flush when dynarec is enabled), including when dynarec is disabled; it keeps candidate addresses and all learned counters. It performs at most 32 guest RAM word reads once on the cold savestate path, with no frame-loop cost. This avoids the known performance loss from clearing/relearning candidate tables. The regression is a model of the promotion threshold; it does not execute the production refresh helper or prove hook placement. The combined endpoint-plus-refresh soak candidate built successfully: EBOOT SHA-256 `b6ccc4aa1924942f963aea6380c85c60ab3c3baeada8ae34acd50e13730c706f`; the ME PRX hash is unchanged. The focused host regression reported 331 checks passed, and the firmware clean build succeeded. A PPSSPP comparison against the frozen full EBOOT then loaded the same H&S heavy state (rc=0) and completed at frame 1001 with all 1,001 video hashes identical and the same audio hash (0b86fceb over 548,916 samples). PPSSPP did not load the ME PRX, so this does not validate PSP rendering, Allegrex cache behavior, or long-session stability. No PSP hardware test has been run; the PSP Go remains unavailable. See `builds/hns-freeze-savestate-refresh-2026-09-24/`.

The highest retained bounded standard-speed fixture rate is approximately 59.8–60 FPS. Separate fast-forward harness windows exceed 100 FPS, but are not benchmark scores or a safety limit. The maximum safe FPS on the PSP Go remains unknown until matched hardware A/B and long-session validation complete. No build is being called a freeze fix yet.

### Adversarial review of the diagnostic candidate (2026-09-24)

An independent source review confirms that the endpoint guard fixes only the table-capacity case where one of the two required gates is absent. It does not establish that either endpoint is a valid instruction boundary, and it cannot help when both installed endpoints are wrong. The savestate refresh prevents the first post-load value comparison from being stale, but leaves accumulated evidence and any installed gates intact across soundtrack or code-role changes when no state load occurs. Neither condition has been observed in a trace from the PSP Go. The model test and PPSSPP output comparisons do not exercise these mechanisms on PSP hardware; the candidate therefore remains diagnostic, and the freeze cause and safe FPS remain unverified.

### Media Engine and dynarec: direct versus indirect interaction

Source inspection finds no direct ME access to the CPU dynarec's translation cache, block tags, or guest CPU register state. `me_render_run()` reads the host-provided VRAM/OAM/palette/capture pointers, copies video inputs into the ME PRX's renderer state, calls `update_scanline()` there, and writes pixels to the supplied staging buffer. With shadow copies enabled, the ME reads copied arrays and the CPU skips the input wait; with shadows disabled, the main CPU waits up to 50 ms for input completion before reusing live arrays. The ME therefore has no source-level path that intentionally modifies translated GBA code or its invalidation metadata.

There is still indirect hardware coupling: the host writes back source buffers, both processors access shared physical memory, the ME uses its own cache operations, and the renderer/GE pipeline changes bus pressure and scheduling. Those effects can change timing or expose a cache-coherency/protocol defect; they could cause stale or incorrect video. A defect in the kernel PRX/reset-vector lifecycle could also affect system stability. None of these is evidence that the ME corrupts dynarec state, and PPSSPP cannot adjudicate them. Turning the ME fully off on the same PSP is a worthwhile factor test; a change in freeze outcome would show dependence on the ME configuration or its timing/resource interaction, not prove direct dynarec corruption.

The fallback path leaves one plausible indirect risk to test: after a stalled renderer misses 30 heartbeat checks, `me_host_watchdog_frame()` calls `me_rend_teardown("watchdog", ...)`; teardown disables frame submission but does not stop or reset the PRX (`psp/me_host.c:183-205`, `psp/main_psp.c:1430-1442`). If the ME is wedged while still touching shared memory, CPU rendering may continue alongside the loaded PRX. When shadow copies are disabled (`g_mer_sh_on == 0`), the main-side input handshake is capped at 50 ms and falls back; this bounds the wait but does not prove the ME has stopped reading its inputs (`psp/main_psp.c:2021-2049`). This is a concrete lifecycle behavior and a plausible bus/memory interaction, not a demonstrated source of dynarec corruption or a verified freeze cause. The PSP audio worker consumes already-mixed samples through a bounded ring; its only unbounded wait is `audio_stop()` awaiting a blocking PSP audio call during teardown (`psp/main_psp.c:598-696`). That could hang exit if the system audio call never returns, but it does not explain a gameplay freeze without entering teardown.

### Historical freeze reports and current status are distinct

The history contains two related but not interchangeable findings. Commit `cae9375` (2026-09-17) documented a real fatal path: speculative translation could patch an unmappable guest exit as a direct Allegrex jump to `0x0FFFFFFC`; Heart & Soul produced 223 such garbage targets from a bad gate, and executing one bypassed `BADJUMP_SAFE`. The current translator contains unmappable exits by patching them to the persistent `bios_swi_entrypoint` and emitting no code. This specifically removes that invalid-native-jump path; it does not prove every freeze has that cause.

A separate experimental build then ran slower and wedged once on a PSP Go (2026-09-18). Its dispatch islands did cause a measured performance regression: hardware A/B showed roughly +16% H&S work and +8% Unbound work, and removing the emitted islands recovered most of that cost. The documents proposed cache-metadata overrun as a possible wedge mechanism, but the later correction explicitly says the Go hard freeze was **not explained**; the A/B established performance causality, not freeze causality. The later 36-run/1,440-state-load soak was on PSP-1000 and PSP-3000, not Go. The user's subsequent Go freeze during play therefore remains unclassified, and the non-Go soak does not clear it.

This chronology makes the dynarec/SMC path the highest-priority software suspect because it has produced a demonstrated fatal jump and a separate Go wedge during an experimental change. It does not support claiming that current M4A optimization caused the later Go freeze. The matched Go `full`/`control` test remains necessary to test whether the current partial-safe runtime group is required for that symptom.

### Documentation claim audit

The release draft copied into both `builds/hns-freeze-endpoint-guard-2026-09-24/source/README-release-draft.md` and the later savestate-refresh snapshot says “a hard freeze found and fixed” (line 53). Its own supporting paragraph narrows that to preventing a demonstrated invalid-native-jump mechanism and admits the original freeze was never reproduced on demand (lines 101–102). The root-cause record and current-state note are more accurate: `docs/STABILITY-FIX-2026-09-17.md:62` and `docs/CURRENT-STATE.md:72` explicitly say the PSP Go freeze has no demonstrated cause. The release headline therefore overstates what the evidence establishes and should not be used as the conclusion of this investigation. `docs/DEBUGGING.md:20–22` also states that a hard freeze with no exception “means” an unmapped translation-cache exit; the evidence supports treating that as a first diagnostic hypothesis, not a proven diagnosis of every such freeze. This wording conflict is relevant because it can make a known containment fix look like a vanquished Go crash.
